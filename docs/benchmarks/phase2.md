# Phase 2 벤치마크 — 측정 계층 도입 전/후 처리량 비교

## 한 줄 결론

- **처리량은 달라지지 않았다.** 5개 시나리오 모두 Phase 1 대비 **-4.5% ~ +2.1%** 안이고, 개선인지 퇴보인지 구분되지 않는 측정 오차 수준이다. **"Phase 2로 빨라졌다"고 주장하지 않는다.**
- 핫패스에 추가된 비용(요청마다 `Recorder.recordValue` + `System.nanoTime()`)은 **이 측정으로는 검출되지 않았다.**
- 피크 플랫폼 스레드는 **37 → 38**(+1). 증가분은 새로 생긴 `metric-sampler` 스케줄러 스레드이고 설계 의도대로다.
- Phase 2의 가치는 처리량이 아니라 **측정의 정확도**다(백분위, 순간 TPS, 실제 구간 평균, JVM 지표, 워커의 전송 부담 제거). 이 문서는 그 대가로 성능을 잃지 않았다는 것만 확인한다.

## 해석

- **S1과 S4가 3.6~4.5% 낮게 나온 것을 퇴보로 읽지 않는다.** 같은 설정인 S5는 반대로 +2.1%이고, S1과 S5의 부호가 엇갈린다. S1·S4는 범위가 겹치거나 맞닿아 있다(S1: 53,763이 양쪽 범위에 모두 있음). 3회 반복으로는 이 크기의 차이를 구분할 수 없다.
- **반대로 "비용이 없다"고도 단정하지 않는다.** 요청당 추가된 일은 매우 작아서(원자적 기록 한 번, 시각 읽기 한 번) 이 하니스의 변동폭(±3%)보다 작을 것으로 보이지만, 그 크기를 이 데이터로 직접 입증하지는 못했다. 확정하려면 반복 횟수를 늘리거나 JMH 같은 마이크로벤치마크가 필요하다.
- **워커의 STOMP 전송 제거(B4)의 이득은 이 벤치마크로 측정되지 않는다.** 하니스에는 구독자가 없어서 `convertAndSend`가 사실상 빈 호출이다. 구독자가 많거나 브로커가 느린 환경에서는 차이가 날 수 있으나, 측정하지 않았으므로 주장하지 않는다.
- 스레드 +1은 `metric-sampler`(플랫폼 스레드 1개, 실행 개수와 무관하게 공유)다. 가상 스레드 워커 수나 HttpClient 스레드 수에는 영향이 없다.

## 새로 측정할 수 있게 된 값 — 실제 구동 확인 (벤치마크 아님)

앱을 실제로 기동하고 **자기 자신의 `/api/tests/health`** 에 300 워커 × 1,500 요청을 걸어 STOMP로 수신한 값이다. 대상 서버가 앱 자신이라 서버 쪽 스레드가 섞여 있고, 단일 실행이므로 **성능 수치로 인용하지 않는다.** 새 지표가 실제 값으로 채워진다는 확인용이다.

| 항목 | 관측 |
|---|---|
| 메트릭 수신 | 약 1초 간격으로 8건 + 완료 1건, 완료 뒤 `RUNNING` 없음 |
| 순간 TPS | 약 61,600–64,400 (구간별) |
| 구간 평균 응답시간 | 5ms (예전에는 항상 0으로 전송) |
| 누적 p95 / p99 | 약 8.3–8.4ms / 10.5–11.0ms |
| 활성 워커 | 300 → 완료 시 0 |
| 캐리어 풀 | 14 (CPU 코어 수) |
| 핀닝 | 0 |

별도 실행(200 워커 × 100 요청)의 저장된 결과에서는 `p50/p90/p95/p99/p99.9 = 3.7 / 8.9 / 12.4 / 24.8 / 41.2ms`, `gcCount 22`, `peakPlatformThreads 159`(앱 서버 스레드 포함)로 DB 컬럼 저장과 조회까지 확인했다.

## 한계

- 단일 머신(Apple Silicon 14코어, macOS)에서 앱·대상 서버·Postgres 컨테이너가 함께 돈다. 같은 조건의 상대 비교로만 의미가 있다.
- 각 코드를 JVM 3회 기동한 중앙값이며 통계 검정은 하지 않았다. ±5% 안의 차이는 해석하지 않는다.
- 대상은 로컬 `HttpServer`(HTTP/1.1, 평문 loopback)이고 전부 `VIRTUAL` 타입이다. `PLATFORM` 실행은 측정하지 않았다(Phase 3 범위).
- 하니스에 STOMP 구독자가 없어 실시간 전송 경로의 비용은 반영되지 않는다.
- 새 지표(JVM 값)의 수집 비용은 1초 주기 샘플러 한 번(MXBean 읽기 몇 번)이며 워커 경로 밖이다. 샘플러 자체의 CPU 점유는 별도로 측정하지 않았다.
- **핀닝은 실행 종료 시 JFR 이벤트 전달을 확정한 뒤의 값이다.** JFR 스트림은 이벤트를 배치로(최대 약 1초) 전달하므로, 전달을 기다리지 않고 최종 스냅샷을 만들면 마지막 구간의 핀닝이 DB 결과에서 영구히 누락되고 다음 실행의 기준선 뒤에 늦게 도착해 잘못 귀속될 수도 있다. 초기 구현은 기다리지 않는 결함이 있었고 코드리뷰로 발견해 고쳤다. 이제 `PinningMonitor.awaitDelivery()`가 호출 이후에 시작된 JFR 플러시 2회를 기다린다(이벤트가 없어도 약 1초 주기로 플러시되며, 반복 시험 15회 모두 확정). 확정 없이 끝난 실행(워커 실패·중단·확정 시간 초과)은 결과를 만들지 못하거나 확정에 실패한 것이므로, 그 늦은 이벤트가 다음 실행의 기준선 뒤에 도착해 섞이지 않도록 **다음 실행이 기준선을 읽기 전에 먼저 확정한다**(정상 종료한 실행 뒤에는 이 추가 대기가 없다). 남는 한계: **제한 시간(`loadtest.pinning-monitor.settle-timeout`, 기본 2초) 안에 확정되지 못하면 일부가 누락될 수 있고**, 동시에 도는 실행끼리는 JVM 전역 값이라 여전히 섞인다. 실시간(주기 샘플) 핀닝 값은 계속 최대 약 1초 늦다.
- **최종 결과의 GC·힙·플랫폼 스레드·피크는 워커 종료 시점의 값이고, 핀닝만 전달 확정 후의 값이다.** 전달 확정을 기다리는 동안(최대 2초)의 GC나 스레드 변화가 이 실행의 몫으로 섞이지 않게, 최종 샘플은 워커 종료 직후에 확정하고 대기 뒤에는 핀닝 수치만 다시 읽는다(코드리뷰 반영). 그래서 저장된 소요 시간과 런타임 지표가 같은 구간을 가리킨다.
- **트레이드오프: 모니터가 켜져 있으면 `COMPLETED` 알림과 결과 반환이 약 1~2초 늦어진다.** 실제 기동에서 실행 74ms짜리의 `COMPLETED`가 약 1초 뒤에 도착했고, 저장된 소요 시간은 74ms 그대로였다(종료 시각을 대기 전에 확정). 기다리지 않으려면 `settle-timeout: 0`으로 두면 되지만 위 누락이 다시 생긴다.
- **피크(힙·플랫폼 스레드)는 연속 측정이 아니라 관측값의 최댓값이다.** 관측 시점은 실행 시작, 워커 기동 직후, 50ms 주기(`loadtest.metrics.peak-sample-interval`), 1초 샘플, 종료 시점이다. 50ms보다 짧은 스파이크는 놓칠 수 있다. 초기 구현은 1초 주기 샘플과 종료 시점만 봐서, 1초보다 짧게 끝나는 실행(이 벤치마크의 한 회 소요가 140~190ms)에서는 PLATFORM 풀 스레드가 피크에 잡히지 않는 결함이 있었고 코드리뷰로 발견해 고쳤다.

## 재현 방법

```bash
# Docker 필요 (Testcontainers Postgres). 평소 ./gradlew test 에서는 실행되지 않는다.
# Phase 2 코드
BENCHMARK=true BENCH_LABEL=p2-1 ./gradlew test --rerun --tests '*PinningBenchmarkTest'
cat build/benchmark/p2-1.md

# Phase 1 코드 (같은 하니스가 이미 들어 있는 커밋)
git worktree add /tmp/p1 416a705
(cd /tmp/p1 && BENCHMARK=true BENCH_LABEL=p1-1 ./gradlew test --rerun --tests '*PinningBenchmarkTest')
git worktree remove --force /tmp/p1
```

- 두 코드를 번갈아 3회 이상 반복하고 각 회의 중앙값을 다시 중앙값으로 집계했다. 한 번의 실행에 약 2~3분이 걸린다.

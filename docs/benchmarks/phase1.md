# Phase 1 벤치마크 — 가상 스레드 사용 방식 개선 전/후

## 한 줄 결론

- **개선의 거의 전부는 `HttpClient`에 가상 스레드 executor를 지정한 한 줄에서 나왔다.** 피크 플랫폼 스레드 **≈200 → 37**, HttpClient 플랫폼 워커 스레드 **≈170 → 0**, 처리량 **약 +100%(S1, S2) / +85%(S3)**.
- **"요청마다 로깅해서 핀닝이 생긴다"는 가설은 반증됐다.** 요청 단위 로그 약 8만 줄을 가상 스레드에서 출력하는 시나리오(S1)에서도 `jdk.VirtualThreadPinned` 이벤트는 **0건**이었다.
- 요청 단위 로깅은 핀닝 원인은 아니지만 비용은 있다(개선 후 약 5~6%, `HttpClient`가 병목이던 구조에서는 약 16~18%). 옵션화(기본 OFF)는 유지하고, 비동기 로그 어펜더는 **이득이 없어 채택하지 않았다.**

## 무엇을 측정했나

| 시나리오 | 조건 | 요청 수/회 |
|---|---|---|
| S1 | 대상이 500 응답 + 요청 로깅 켬 (V1 핀닝 가설 검증용) | 200 VU × 50 = 10,000 |
| S2 | 정상 200 응답 + 로깅 끔 | 1,000 VU × 10 = 10,000 |
| S3 | 200 응답 + 20ms 지연 (고동시성) | 1,500 VU × 6 = 9,000 |
| S4 | S1과 같은 조건에서 로깅만 끔 (개선 전 코드는 이 옵션을 무시 → S1과 동일) | 200 VU × 50 |
| S5 | S1 재측정 (마지막에 다시 돌려 **실행 순서 효과**를 확인) | 200 VU × 50 |

- 시나리오마다 워밍업 1회 + 측정 3회. 그 위에 **전체 시나리오를 한 번 통째로 돌린 워밍업 패스**를 두고 두 번째 패스만 기록한다.
- 각 조건을 벤치마크 JVM 기동 3회 반복해 **중앙값(범위)** 을 냈다.
- 지표: TPS, 피크 플랫폼 스레드(`ThreadMXBean`, JVM 전체 절대값), 생존 `HttpClient-*-Worker-*` 스레드 수, JFR `jdk.VirtualThreadPinned` 이벤트(임계값 1ms).
- 측정 대상은 앱의 `TestExecutionService.executeTestWithId` 전체 경로(HTTP 호출 + WebSocket 전송 + DB 저장)다.

## 결과

### 개선 전 vs 개선 후 (TPS는 중앙값, 괄호는 범위)

| 시나리오 | 개선 전 TPS | 개선 후 TPS | 변화 |
|---|---|---|---|
| S1 500+로깅 켬 | 25,773 (24,213–26,110) | 54,054 (53,763–54,945) | **+110%** |
| S2 200, 1,000 VU | 33,223 (31,447–34,130) | 70,423 (68,493–74,074) | **+112%** |
| S3 200 + 20ms, 1,500 VU | 26,471 (26,393–26,946) | 49,180 (46,632–52,326) | **+86%** |
| S4 500+로깅 끔 | 25,063 (개선 전엔 옵션 무시) | 57,471 (57,471–57,471) | +129% |
| S5 (S1 재측정) | 25,189 (24,691–25,907) | 54,645 (53,476–54,945) | +117% |

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 피크 플랫폼 스레드(중앙값, 시나리오별 범위) | 199–223 (범위 199–229) | **37** (37–37) |
| 생존 HttpClient 워커 스레드 | 162–186 | **0** |
| 핀닝 이벤트 (전 시나리오·전 실행 합) | **0** | **0** |

개선 전 = 커밋된 원본 코드(`CompletableFuture` 기반, `HttpClient` 기본 executor) + 측정 도구만 추가한 상태. 개선 후 = 이 문서 시점의 코드.

### 어느 변경이 효과를 냈나 — ablation

개선 후 코드에서 `HttpClient`의 `.executor(...)` **한 줄만 제거**하고 같은 조건으로 측정했다.

| 시나리오 | 개선 전 | `.executor()`만 뺀 개선 후 | 개선 후(전체) |
|---|---|---|---|
| S1 | 25,773 | 24,876 | 54,054 |
| S2 | 33,223 | 32,680 | 70,423 |
| S3 | 26,471 | 27,950 | 49,180 |
| S4 (로깅 끔) | 25,063 | 29,240 | 57,471 |
| 피크 스레드(S2) | 207 | 211 | 37 |

- `.executor()`를 빼면 개선 전과 사실상 같은 수준으로 돌아간다(S1~S3 ±6% 이내, 스레드 ≈210). 즉 `TestRunContext` 도입, 실행 단위 executor(`CompletableFuture` 제거), 컨트롤러의 `commonPool` 제거는 **성능에 영향이 없는 구조 개선**(격리·종료 보장·테스트 용이성)이고, **처리량과 스레드 수 개선은 HttpClient executor 지정에서 나왔다.**
- 이유: `HttpClient`에 executor를 주지 않으면 JDK가 캐시드 **플랫폼** 스레드 풀을 만든다. 워커는 가상 스레드인데 HTTP 클라이언트 내부 작업이 그 플랫폼 스레드 수에 묶여, 동시 요청이 많을수록 플랫폼 스레드가 150~190개로 늘고 처리량이 그 풀에 제한된다.
- 로깅을 끈 효과(S4 vs 켠 S1·S5)는 `.executor()`가 없을 때 약 +16~18%(24,876·25,253→29,240), 있을 때 약 +5~6%(54,054·54,645→57,471)로 나타났다(아래 참조).

## V1 핀닝 가설 검증

**가설(로드맵 V1)**: "요청마다 `log.warn`을 호출하면 기본 콘솔 어펜더의 `synchronized` 때문에 가상 스레드가 캐리어 스레드에 핀닝된다."

**전제 확인**: 이 프로젝트의 Logback은 1.5.21로 `ConsoleAppender → OutputStreamAppender → UnsynchronizedAppenderBase`이며 쓰기 락은 `ReentrantLock`이다(`javap` 확인). JDK 21 `System.out`도 내부적으로 `ReentrantLock`을 쓴다. 즉 가설의 전제("기본 어펜더는 `synchronized`")가 사실이 아니었다.

**측정 결과**: 핀닝 **0건**(S1: 500 응답 10,000건 × 로깅 켬, 워밍업 포함 약 8만 줄 이상 출력).

**이 "0건"을 믿을 수 있는 이유**
- `PinningMonitorTest`가 `synchronized` 안에서 `Thread.sleep`하는 가상 스레드를 **일부러 만들어** 모니터가 실제로 감지하는지 확인한다(도구가 핀닝을 볼 수 있다는 증명).
- 벤치마크는 시작 시 모니터가 실행 중인지를 단언한다.
- 실제로 로그가 출력됐음을 확인했다(가상 스레드 `virtual-N`에서 `HTTP Error: 500` 라인 다수).

**결론**: 가설은 반증됐다. 이 스택에서 요청 로깅은 핀닝 원인이 아니다.

**한계**: 임계값 1ms 미만의 짧은 핀닝은 기록하지 않는다. JDK 24(JEP 491)부터 `synchronized` 핀닝 자체가 사라지므로 이 계측은 Java 21~23에서만 의미가 있다. 다른 경로(예: TLS 연결)의 핀닝은 이 시나리오(HTTP 평문, 로컬)로는 검증하지 못했다.

## 요청 로깅의 비용과 비동기 어펜더

- 핀닝은 없지만 로깅 I/O 자체의 비용은 있다. 개선 후: 로깅 켬(S1 54,054 / S5 54,645) vs 끔(S4 57,471) → **약 5~6%**. `HttpClient`가 병목이던 구조(ablation)에서는 켬(24,876 / 25,253) vs 끔(29,240)이 **약 16~18%** 차이였다.
- `TestConfigDto.isEnableLogging()`이 어디서도 호출되지 않던 죽은 코드였던 것을 실제로 배선해, 요청 단위 로그는 **켰을 때만** 출력한다(기본 OFF). 에러는 이미 `errorBreakdown`에 집계되므로 기본에서도 정보 손실이 없다.
- **비동기 콘솔 어펜더(`AsyncAppender`, `neverBlock=true`)는 채택하지 않았다.** 같은 조건에서 S1 55,249(54,054–55,556) vs 동기 54,054 — 차이가 측정 오차 안이다. 이득이 없는 설정은 넣지 않는다는 사전 기준에 따라 제외했다. (측정 콘솔은 Gradle 워커의 파이프이며 실제 터미널·파일 어펜더에서는 다를 수 있다.)

## 측정 과정에서 발견한 함정 (신뢰성 기록)

이 벤치마크를 만드는 동안 **측정 환경 자체가 결과를 왜곡**하는 경우가 세 번 있었고, 그때마다 잘못된 결론에 도달할 뻔했다.

1. **대상 서버의 accept 백로그** — 대상 서버(JDK `HttpServer`)의 백로그가 작고 macOS `kern.ipc.somaxconn=128`이라, 수천 연결이 동시에 몰리면 SYN이 버려져 ~1초 단위 재전송 지연이 생겼다. 같은 코드의 TPS가 1,700 ↔ 25,000으로 두 갈래로 요동했다. → 백로그를 4096으로 요청(OS 상한이 실효값을 제한).
2. **대상 서버의 유휴 연결 상한** — `sun.net.httpserver.maxIdleConnections` 기본 200. 클라이언트가 수천 연결을 재사용하면 서버가 유휴 연결을 먼저 닫아, 방금 닫힌 연결에 요청을 쓴 클라이언트에서 **간헐적 실패(UNKNOWN, 30,000건 중 1~2건)** 가 났다. HttpClient executor 변경 직후에만 나타나 개선의 부작용처럼 보였으나, 대상 서버 상한을 풀자 실패 0건, S2/S3 TPS가 50~60k대로 안정됐다(가설 검증됨). 즉 **앱의 문제가 아니라 측정용 대상 서버의 한계**였다.
3. **첫 시나리오의 콜드 스타트** — S1(첫 시나리오)이 S4·S5보다 유독 낮게(≈31k vs ≈57k) 나와 "로깅을 끄면 +80%"라고 해석할 뻔했다. 같은 조건을 마지막에 다시 측정한 S5가 57k로 나와 **실행 순서에 따른 워밍업 부족**임이 드러났다. → 전체 워밍업 패스를 추가했고, 이후 S1≈S5(순서 효과 없음).

교훈: 개선을 주장하기 전에 **같은 조건을 반복·재배치해서 측정 자체를 검증**해야 한다. 위 1~3을 고치기 전의 수치는 이 문서에 쓰지 않았다.

## 한계

- 단일 머신(Apple Silicon 14코어, macOS)에서 **앱·대상 서버·Postgres 컨테이너가 함께** 돈다. 절대 수치보다 **같은 머신·같은 조건의 상대 비교**에 의미가 있다.
- 대상은 로컬 `HttpServer`(HTTP/1.1, 평문 loopback)이다. 실제 원격 서비스·TLS·HTTP/2에서는 결과가 다를 수 있다(프로토콜 비교는 Phase 3).
- 벤치마크 JVM 3회 반복의 중앙값이며 통계적 유의성 검정은 하지 않았다. 다만 범위가 좁고(개선 후 S2 68–74k vs 개선 전 31–34k) 방향이 일관된다.
- 벤치마크가 쓰는 Postgres(Testcontainers) 컨테이너도 같은 머신에서 돌므로 DB 저장 비용이 결과에 섞여 있다(실행당 1회 INSERT).
- 피크 스레드는 JVM 전체(Spring/Tomcat/DB 풀 포함) 절대값이다.
- 요청 로깅의 비용은 콘솔이 Gradle 파이프인 조건에서만 측정했다.

## 재현 방법

```bash
# Docker 필요 (Testcontainers Postgres). 평소 ./gradlew test 에서는 실행되지 않는다.
BENCHMARK=true BENCH_LABEL=my-run ./gradlew test --rerun-tasks --tests '*PinningBenchmarkTest'
cat build/benchmark/my-run.md
```

- 개선 전 코드를 재측정하려면 원본 커밋을 체크아웃한 worktree에 `PinningMonitor.java`, `PinningBenchmarkTest.java`, `FakeTargetServer.java`만 복사해서 같은 명령을 실행하면 된다(벤치마크는 Spring 컨텍스트에서 빈을 주입받으므로 서비스 생성자 시그니처에 의존하지 않는다).
- 한 번의 실행에 약 2~3분이 걸린다. 결과의 변동은 벤치마크 JVM을 3회 이상 반복해서 확인할 것.
